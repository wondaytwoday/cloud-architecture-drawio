## 2단계: 라우터와 진단

`evals/bench_routing.py`로 고정 코퍼스 841개 모델을 1단계 라우터와 비교했습니다. 코퍼스는 다음으로 구성됩니다:
- 예제 5개와, 같은 예제의 포트를 모두 auto로 바꾼 것
- 무작위 격자: 라벨 유무, 레인 74/100/144px
- 촘촘한 모델 8×8 ~ 12×16
- 라벨 있는 1→N 분기
- 서브넷 경계가 있는 모델

| 지표 | 1단계 | 2단계 |
|---|---:|---:|
| 빌드 성공 | 547 | **785** |
| 경로 실패 | 210 | **0** |
| 라벨 실패 | 84 | 56 |
| 기존 성공 중 새로 실패 | | **0** |

양쪽 모두 성공한 모델 547개를 비교하면 다음과 같습니다:
- 교차: 876 → 732
- 꺾임: 6,797 → 6,857 (+0.9%)
- 경로 길이: +0.1%
- 짧은 계단(12px 이하 내부 구간): 603 → 613
- 컨테이너 테두리에 4px 이내로 붙어 달린 길이: 20,167 → 1,554px
- 꺾임을 넘어 4px 이상 튀어나온 캡션: 78 → 12
- 다른 연결선에 6px 이내로 붙은 캡션: 43 → 5

앞의 두 항목은 다른 선의 라벨처럼 읽힐 수 있는 캡션이라, 1단계보다도 줄였습니다.

빡빡한 간격도 1단계와 같습니다. 위아래로 놓인 카드는 2 × stub(32px), 옆으로 놓인 카드는 캡션 상자 폭 + 8px부터 빌드되고, 간격을 넓혀서 실패하는 구간은 없습니다. 이는 회귀 테스트로 고정했습니다.

예제 결과:
- aws-three-az의 교차가 2 → 0이 됐습니다.
- 모든 예제의 꺾임과 경로 길이는 1단계와 같습니다.
- 바뀐 선 대부분은 테두리에서 떨어진 위치로 옮겨졌습니다. 다만 Azure private-link와 GCP psc-service는 열린 공간에 있던 꺾임이 VNet/VPC 경계 안쪽 10px 레인으로 옮겨졌습니다.
- 캡션은 대부분 자기 선분 안쪽, 다른 선과 떨어진 자리로 옮겨졌습니다.

바뀐 동작:
- **리드인 예약**: 포트를 먼저 정하므로 모든 리드인을 미리 압니다. 아직 그리지 않은 연결선의 리드인을 먼저 그리는 선이 막거나 지나가지 못합니다. 경로 실패의 원인 대부분("No route", "lead-ins overlap")이 이것이었습니다.
- **테두리 회피**: 컨테이너 테두리에서 8px 이내로 평행하게 달리면 비용을 더하고, 테두리 ±10px에 탐색 격자선을 둡니다.
- **평행선 벌리기**: 라벨이 들어가지 않으면 수평 40px·수직 60px 이내로 나란히 달리는 선에 비용을 더해 다시 시도합니다. 1→N 분기가 모두 성공하게 됐습니다.
- **대체 시도**: 위 제약은 드물게 라벨 자리를 없애므로 12가지 방식을 차례로 시도합니다.
  - 순서: 예약 → 예약 해제, 각각 평행선 벌리기 없음 → 있음, 각각 테두리 회피 있음 → 없음.
  - 예약한 경우에는 예약한 리드인 옆 격자선 없이 먼저 시도하고, 다음에 격자선을 넣어 시도합니다. 격자선을 늘 넣으면 10px 계단이 늘었기 때문입니다.
  - 어느 방식이든 성공하면 성공이고, 쓰인 방식은 리포트의 `routing`에 남습니다.
- **라벨 배치**:
  - 후보는 약 6px 간격 위치, 선분 중점, 1단계의 고정 비율 위치를 모두 씁니다.
  - "선분 밖으로 튀어나오지 않고 다른 선과 8px 이상 떨어진 자리"를 먼저 고르고, 없으면 조건을 하나씩 완화합니다.
- **성능**: 장애물과 기존 선을 격자선별로 색인해 경로 탐색이 3~5배 빨라졌고, 출력은 바이트 단위로 같습니다. 성공하는 모델이 늘고 대체 시도가 생겨 전체 벤치마크 시간은 40초 → 66초입니다.
- **진단**:
  - 라벨 실패를 한 번에 모두 보고합니다. 항목마다 캡션 크기, 가장 긴 구간, 막는 도형 이름이 붙습니다. 가로 구간이 짧을 때는 필요한 길이를, 길이가 충분할 때는 옆의 도형을 떨어뜨리라고 안내합니다.
  - 리드인 오류는 부딪힌 카드나 제목과, 정확히 몇 px 옮기면 되는지를 알려 줍니다.
  - 포함 오류는 몇 px 벗어났는지를 알려 줍니다.
- **`check` 명령**:
  - validate → build → render를 한 번에 판정합니다. 종료 코드는 0 성공, 1 실패, 2 렌더 환경 없음(브라우저 미설치 포함)입니다.
  - 출력 이름이 `.png`·`.svg`·`.json`이면 원본을 덮지 않도록 거부합니다.
  - 렌더러는 `~/.cache/cloud-architecture-drawio`에 한 번 설치해 재사용합니다.
- **검토**: 2단계 변경분을 독립 에이전트로 다시 검토했습니다. 확인된 문제 13건과 직접 재현해 확인한 시각 문제 3건을 고쳤고, 주요 기능은 끄면 테스트가 실패하도록 변이 시험으로 확인했습니다.
  - 확인된 13건: 중점이 빠진 라벨 후보, 튀어나오거나 다른 선에 붙은 캡션, `check`의 출력 덮어쓰기와 브라우저 미설치 처리, 진단 수치, 테스트 공백, 문서 순서 오류 등
  - 시각 문제 3건: 계단, 캡션 돌출, 캡션 근접
  - 변이 시험 대상: 대체 시도, 평행 분산, 오류 선택, 예약, 테두리 비용, 캡션 단계 선택

남은 한계:
- 74px 좁은 레인과 서브넷 기둥 사이의 라벨 실패가 남아 있습니다(56건). 이런 경우 오류가 넓혀야 할 위치와 막는 도형을 알려 줍니다.
- 포트 면을 라우터 안에서 후보로 탐색하는 기능과, 라우팅 후 선 간격을 고르게 하는 nudging은 넣지 않았습니다.
- 라우터 관점의 독립 검토는 사용량 한도로 완료되지 않았습니다. 그 대신 다음을 직접 확인했습니다.
  - 순서 무관성: 모델 16개에 대해 간선·노드·컨테이너 순서를 세 번씩 섞어 봤고, 결과가 모두 같았습니다.
  - 실행 시간: 대체 시도가 모두 실패하는 큰 모델은 오래 걸렸습니다(노드 60개·간선 120개 162초).
  - 그래서 모든 방식이 합쳐 쓸 수 있는 탐색 단계를 150만 회로 제한했습니다. 이제 같은 모델은 29초 뒤에 "뷰를 나누라"는 안내와 함께 멈춥니다.
  - 상한은 시간이 아니라 탐색 횟수 기준이라 기계와 상관없이 결과가 같습니다. 벤치마크의 최대 사용량은 52만 회라 영향이 없습니다.

## 1단계: 검사 신뢰성
v3 1단계는 검사를 통과했는데도 틀린 그림이 나오던 경로를 막았습니다. 독립 검토 에이전트들이 재현한 문제를 근거로 고쳤고, 고친 뒤 같은 재현 모델로 다시 확인했습니다. 라우터 알고리즘은 바꾸지 않았습니다. 그래서 1단계 시점에는 다섯 예제의 경로·라벨·지표가 v2와 같았습니다. 현재 수치는 위 2단계 결과를 보세요.

## 이전 기록: v2, 2026-09-28

AWS·Azure·GCP 예제에 스킬을 적용하고 실제 draw.io viewer 엔진으로 렌더링했습니다. 별도 에이전트가 구조·라우팅 테스트와 이미지 검수를 수행했고, 발견한 오류를 수정한 뒤 다시 검증했습니다. 아래 수치는 이 다섯 예제의 결과이며 임의 아키텍처 전체에 대한 성능 보장은 아닙니다.

기존 경로와 새 경로를 동일한 지표 함수로 측정했습니다. 교차는 서로 다른 엣지 쌍의 교차 좌표를 세며, 두 엣지의 공통 종점은 제외합니다. 중첩 길이는 엣지 쌍별로 같은 직선 구간을 공유하는 길이의 합입니다. 박스 경계와의 교차는 통신선 교차 지표에 포함하지 않습니다.

이 비교에는 라우터 개선과 템플릿의 포트·여백·제목 위치 조정이 함께 포함됩니다. 라우터 단독 비교는 아닙니다. 전체 꺾임 수는 92 → 97로 늘었습니다. 짧은 경로보다 명확한 연결 지점과 분리된 선을 우선한 결과입니다. [기존 경로·이미지](before-routing/)와 [기존 수치](routing-before.json)를 보관했습니다.

3-AZ의 남은 두 교차는 DB로 향하는 서로 독립적인 경로입니다. 실제 렌더에서 점프 아크 2개를 확인했고, 생성 보고서에 검수 경고로 남겼습니다. 경고를 숨기거나 교차를 연결 지점으로 바꾸지 않았습니다.

### 검증한 항목

- 회귀 테스트 **43개 통과**. 카드·제목 장애물, 포트 분산, 명시 포트 예약, 모든 선에 대한 라벨 충돌, 입력 엣지 순서 독립성, XML 참조, 잘못된 입력, CSP 경계, 한글 텍스트 길이, 추가 AZ에 가려지는 논리 그룹을 검사합니다.
- 공식 스킬 검사: Skill is valid!
- 5개 예제 총 **59개 연결선과 59개 라벨**의 실제 렌더 좌표가 생성 보고서와 일치합니다. 라벨 앵커는 draw.io의 픽셀 반올림을 고려해 0.51 px 허용합니다.
- 5개 렌더 모두 JavaScript 오류·누락 아이콘·깨진 이미지 0.
- 실제 Graph 모델에서 연결된 리소스를 이동·복원하고, 라벨이 있는 연결선과 양 끝점을 함께 이동하여 라벨이 따라오는지 확인했습니다. XML 저장·재파싱 후 source/target와 라벨의 상대 부모 관계도 보존됩니다.
- 별도 [교차 fixture](fixtures/routing-crossings.png)로 한 번 교차하는 두 선의 점프 아크를 확인했습니다. 모델 지표 1회, 실제 렌더 마커 1개가 일치합니다.
- PNG 전체와 복잡한 영역을 눈으로 검수했습니다. AWS 3-AZ는 별도 검수에서 발견한 그룹 경계 가림을 수정하고 재렌더링했습니다.

기계 판독 결과, 모델 해시, viewer SHA-256: [results.json](results.json). 각 예제 옆에 모델, SVG, 생성 보고서, 렌더 보고서가 함께 있습니다.

### 이번 반복에서 고친 문제

1. 같은 카드 측면의 입·출력 선이 한 점에 몰림 → 양방향 연결을 함께 분산하고 수동 포트를 먼저 예약합니다.
2. 선이 기존 선과 포개짐 → 양의 길이를 공유하는 경로를 금지하고, 교차·꺾임·가까운 평행선에 비용을 부여합니다.
3. 먼저 배치한 라벨을 나중 선이 관통 → 모든 경로를 만든 후 전체 선·리소스·제목·경계와 충돌 검사합니다.
4. 라벨이 독립 텍스트여서 선 편집 시 남겨짐 → 실제 연결선의 상대 좌표 자식 셀로 만들었습니다.
5. AWS 3-AZ 추가 시 서브넷 배경이 논리 그룹을 덮음 → 부모 순서를 지키면서 일반 컨테이너보다 overlay를 나중에 그립니다.
6. 관리형 서비스가 하위 그룹을 거쳐 서브넷 안에 숨음 → 전체 상위 경계를 검사합니다. Azure/GCP 서브넷의 리전 범위와 공급자별 VPC/VNet도 검사합니다.
7. 예약 ID, 잘못된 형식·좌표, 긴 페이지/범례 텍스트 → 생성 전에 수정 가능한 오류로 보고합니다.
8. Azure의 모호한 Gateway subnet → App Gateway subnet; GCP 로드밸런서에는 global external ALB 모드를 명시했습니다.

### 재현 및 범위

회귀 테스트: `python3 -m unittest discover -s evals -v`

예제 재생성: `python3 cloud-architecture-drawio/scripts/cloud_drawio.py build examples/aws-three-az.model.json examples/aws-three-az.drawio`

렌더 재현은 [절차](../cloud-architecture-drawio/references/rendering.md)를 따릅니다. 기존 Node/Playwright 설치와 기록된 viewer를 사용할 수 있습니다.

- 36개 CSP 벡터 아이콘을 포함합니다. 전체 최신 아이콘 목록은 아니며, GCP는 draw.io gcp2 계열입니다.
- 에이전트가 배치와 의미를 선택하고 생성기가 경로를 계산합니다. 임의 규모 자동 배치나 전역 최적 경로를 보장하지 않습니다. 복잡한 토폴로지는 페이지 분리 또는 native XML 편집이 필요할 수 있습니다.
- 일부 구조·서비스 범위 검증이며 실제 라우팅·방화벽·DNS 도달 가능성 검증은 아닙니다. AWS NAT의 상세 egress와 서브넷 attachment는 예제 주석대로 생략했습니다.
- draw.io Desktop이 없어 실제 viewer의 Graph 엔진에서 검증했습니다. 데스크톱 에디터 UI 수동 조작 테스트와는 구분합니다.
- 편집 가능한 waypoint를 저장하므로 이후 수동으로 도형을 이동하면 주변 전체 선의 최적화·충돌 검사가 자동 실행되지는 않습니다. 모델 기반 변경은 재빌드·재렌더링하고, 수동 편집본은 원본을 보존해 필요한 셀만 수정합니다.
